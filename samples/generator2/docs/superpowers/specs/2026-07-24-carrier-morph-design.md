# Метаморфоза несущей — дизайн

Дата: 2026-07-24

## 1. Цель

Сейчас форма несущей выбирается из библиотеки один раз и держится постоянно. Добавить режим
**метаморфозы**: до трёх форм несущей на канал, которые сменяют друг друга по кругу во время
генерации.

Два способа смены:

1. **Ступень** — форма держится почти весь шаг `T`, затем за ~5 мс сменяется на следующую.
2. **Плавно** — форма непрерывно перетекает в следующую, полный переход занимает `T`.

## 2. Решения (зафиксированы при брейнсторме)

| Вопрос | Решение |
|---|---|
| Цикл форм | По кругу `A→B→C→A`, бесконечно. |
| Смысл `T` | Одно время на весь режим, `T` = длительность **одного шага**. Полный круг = `N·T`. |
| Анти-щелчок в Ступени | Кроссфейд ~5 мс в конце шага. Период шага остаётся ровно `T`. См. §4.4 — почему не оборот фазы. |
| Место в UI | Новая карточка `CardMorph` между `CardCarrier` и `CardAM`. |
| Связь со старой несущей | 3 независимых слота. При `Morph_EN` спиннер в `CardCarrier` гаснет, старая форма сохраняется и возвращается при выключении. |
| Число форм | Галочка вкл/выкл на каждый из 3 слотов. Активные слоты идут по кругу в порядке номеров. |
| Где считать | Посэмплово в нативе, через пару указателей и коэффициент смешивания. |
| Математика смешивания | Линейный лерп (не equal-power). |

## 3. Архитектура

Всё в нативе (`app/src/main/cpp/generator/`), как мастер-громкость: там уже живут буферы форм
и пофреймовое состояние в `StructureCh`. Каждый канал — свой набор.

### 3.1 Состояние в `StructureCh` (`renderchannel.h`)

```cpp
float    buffer_morph[3][1024] = {{0.0f}};  // 3 слота форм несущей, -1..1
uint8_t  morph_slot      = 0;               // форма, из которой перетекаем (0..2)
uint8_t  morph_slot_next = 0;               // форма, в которую перетекаем (0..2)
uint32_t morph_phase     = 0;               // DDS-фаза шага, полный оборот = один шаг
uint32_t morph_fade_phase = 0;              // окно кроссфейда Ступени, зафиксировано на шаг
```

Kotlin-`StructureCh` — только `var buffer_morph: Array<FloatArray> = Array(3) { FloatArray(1024) }`
(нужно для загрузки форм через `sendBuffer`; слоты и фаза живут только в нативе).

Пара слотов хранится целиком, а не выводится из маски на лету. Иначе снятие галочки с целевого
слота посреди шага мгновенно подменило бы `pB` — скачок до половины шкалы. Пара фиксируется на
границе шага и внутри шага не меняется (§10).

### 3.2 Ядро: пара указателей + `t`

Обе формы читаются по одному и тому же фазовому индексу `phase_accumulator_carrier >> 22`,
поэтому смешивание на выходе тождественно равно смешиванию таблиц. Перед циклом рендера
считаем `pA`, `pB` и параметры шага; внутри цикла в каждой из 4 веток вместо
`buffer_carrier[idx]` идёт:

```cpp
float t = t_of(morph_phase);                   // кривая зависит от режима, §4.1
float c = pA[idx] + t * (pB[idx] - pA[idx]);
```

`t` пересчитывается каждый сэмпл. `pA`/`pB` пересчитываются только на границе шага — то есть
раз в `T` секунд, а не каждый сэмпл.

Единый путь вычисления сэмпла, ветвлений в горячей формуле нет. Вырожденные случаи
покрываются данными:

| Ситуация | `pA` | `pB` | `t` |
|---|---|---|---|
| Метаморфоза выключена | `buffer_carrier` | `buffer_carrier` | 0 |
| Активных слотов 0 | `buffer_carrier` | `buffer_carrier` | 0 |
| Активен 1 слот | этот слот | этот же слот | не важен, `pA == pB` |
| Режим Ступень, ≥2 слота | текущий | следующий активный | 0, в конце шага 0→1 |
| Режим Плавно, ≥2 слота | текущий | следующий активный | 0..1 линейно |

Цена при выключенной метаморфозе: +1 загрузка и +2 флопа на сэмпл.

## 4. Математика

### 4.1 Шаг как DDS-фаза

Шаг отсчитывается **фазовым аккумулятором**, как всё остальное в этом рендере: полный оборот
`morph_phase` (uint32) = один шаг длиной `T`.

```
steps = max(1, round(clamp(T, 0.1, 100) * sampleRate))   // morphSteps(), §5.2
inc   = max(1, 2^32 / steps)                             // прирост фазы шага на сэмпл
morph_phase += inc                                       // каждый сэмпл; переполнение = граница
```

Так `t` не сбивается, когда пользователь крутит `T` во время генерации: меняется `inc`, а сама
фаза остаётся на месте, поэтому позиция внутри шага сохраняется точно. Счётчик сэмплов такой
устойчивости не даёт — при уменьшении `T` накопленное значение оказывается за новым концом
шага, и `t` скачком уходит в единицу (слышимый щелчок при перетаскивании регулятора).

Кривая `t` — единственное, чем режимы отличаются:

```
Плавно:   t = morph_phase / 2^32                      // линейно весь шаг, 0..1

Ступень:  fade_phase = fade_samples * inc             // ~5 мс в единицах фазы
          fade_start = 2^32 - fade_phase
          t = morph_phase < fade_start
                ? 0
                : (morph_phase - fade_start) / fade_phase
```

`fade_samples = 0.005 · sampleRate`, зажимается сверху длиной шага. Считать от частоты
дискретизации обязательно: приложение переключается на 192 кГц там, где устройство тянет
(`AudioMixerPump`), и фиксированное число сэмплов дало бы там 1.25 мс вместо 5 мс. Анти-щелчок
мастер-громкости считается так же. Зажим по длине шага не срабатывает никогда (минимальное
`T` = 0.1 с — это 4800 сэмплов при 48 кГц), он на случай экзотических частот.

**Окно кроссфейда фиксируется на шаг.** `morph_fade_phase` берётся из текущего `T` только на
границе шага (и в начале шага, где `t` и так ноль). Новая длина шага при этом действует сразу —
меняется `inc`. Причина: `fade_start = 2³² − fade_phase`, поэтому пересчёт окна сдвинул бы его
под неподвижной фазой и скачком изменил `t`. Смена `T` в момент, когда фаза уже внутри окна,
давала бы щелчок — а регулятор `T` перетаскиваемый и шлёт много мелких изменений подряд.

В обоих режимах `t` лежит в [0, 1): фаза дискретна, поэтому последний сэмпл шага не попадает
ровно в 2³². В Ступени недобор ограничен `1/fade_samples` = 1/240, то есть остаточная ступенька
не больше `|B−A|/240` ≈ −48 дБ полной шкалы. Значение 1.0 достигается фактически — на первом
сэмпле следующего шага, где та же форма играет уже как `pA` при `t=0` (§4.3). Кламп в коде
стоит на случай смены `T` и в норме не срабатывает.

### 4.2 Почему линейный лерп, а не equal-power

Линейный лерп по общему фазовому индексу — это буквально морфинг геометрии волны: синус
линейно превращается в пилу, промежуточная форма есть среднее двух. Equal-power (sin/cos)
кроссфейд дал бы на середине по 0.707 от каждой формы — для коррелированных форм это перелёт
по амплитуде и искажение геометрии.

Побочный эффект линейного: если две формы противофазны (синус и инвертированный синус), при
`t=0.5` получится тишина. Нормализацию не делаем — формы в библиотеке коррелированы.

### 4.3 Граница шага — общая для обоих режимов

```
c = pA[idx] + t*(pB[idx] - pA[idx]);

prev = morph_phase;
morph_phase += inc;
if (morph_phase < prev) {                          // шаг завершён
    morph_slot      = morph_slot_next;
    morph_slot_next = next(morph_slot, morph_mask);
    pA = buffer_morph[morph_slot];                 // пересчёт указателей
    pB = buffer_morph[morph_slot_next];            // раз в T секунд
}
```

Разрыва на границе нет по построению, и это верно для обоих режимов: в конце шага k форма
равна B при `t→1`, в начале шага k+1 `pA` становится **тем же** B при `t=0`. Именно ради этого
`morph_slot` принимает значение `morph_slot_next`, а не пересчитывается заново из маски.

### 4.4 Почему в Ступени кроссфейд, а не оборот фазы

Изначально планировалось менять форму в момент переполнения `phase_accumulator_carrier` —
в расчёте на то, что все таблицы начинаются с нуля и стык будет незаметен. Замер реальной
библиотеки `assets/Carrier/` это опроверг:

| Форма | значение в индексе 0 |
|---|---|
| Sine | 0.0002 |
| Ramp | 0.0037 |
| Dnramp | 0.9985 |
| HWave | 1.0000 |
| HWave2 | 1.0000 |
| Square | 1.0000 |

Половина библиотеки начинается с единицы. Переход Sine → HWave2 на обороте фазы даёт скачок
0 → 1.0 при полной шкале 2.0 — это в 157 раз больше самого большого естественного приращения
внутри Sine (0.0063). Громкий щелчок на каждом переключении.

Оборот фазы вдобавок ничем не выделен: обе таблицы читаются по одному индексу, поэтому `|B−A|`
в индексе 0 не лучше любого другого индекса. Для пары Sine→Square разница в индексе 0 равна
0.9998, а в индексе 253 — ровно 0.0000.

Кроссфейд за ~5 мс не зависит от содержимого таблиц и работает для любой пары. Слух
воспринимает 5 мс как мгновенное переключение, так что «резкость» режима сохраняется.

Побочная выгода: из четырёх веток рендера уходит детект оборота несущей (`prev`/`wrapped`),
и оба режима сводятся к одной формуле с разной кривой `t`.

### 4.5 `next()`

Следующий установленный бит маски по кругу от текущего слота. Если активен один слот —
возвращает его же. Если маска пустая — метаморфоза не активна и `next()` не вызывается.
Отдельной функции «первый активный слот» нет: `next()` сама уводит с погасшего слота и при
этом сохраняет порядок обхода.

[MOR] [Ступень] [Плавно] [T: 2.0 c]       ← строка 1: две кнопки режима, не дропдаун

частоты при FM в режиме min/max (`carrierEnable` в `cardCarrier.kt:55`). Поле частоты несущей
метаморфоза не трогает.

## 10. Крайние случаи

| Случай | Поведение |
|---|---|
| Активных слотов 0 | `morph_mask == 0` → `morphEffective` даёт `false`, играет обычный `buffer_carrier`. Тишины нет. |
| Активен 1 слот | `pA = pB` → постоянно эта форма, смешивание вырождается. Спецветка не нужна. |
| Текущий слот погас на ходу | Доигрывает до конца шага, затем цикл уходит на следующий активный. Задержка ≤ `T`, щелчка нет. Снятая галочка означает «выбывает из цикла», а не «замолкает немедленно». |
| Целевой слот погас на ходу | Пара `(slot, slot_next)` фиксирована на весь шаг, поэтому `pB` не подменяется — щелчка нет. Шаг доигрывает в старую цель, дальше цикл идёт по актуальной маске: до полного схождения ещё один шаг. |
| Оба слота пары вне маски | Доигрывать нечего, а ждать границы значит держать снятую пользователем форму до 100 с. Поэтому здесь единственное исключение: пара снимается на активный слот немедленно, с обнулением фазы. Возникает при включении `MOR` после перенастройки галочек. |
| Слотов было 1, стало ≥2 | Цель ещё не задана (`slot_next == slot`), поэтому `morph_phase` сбрасывается в 0 и морфинг стартует с начала шага. Иначе `t` уже был в середине и подстановка новой цели дала бы скачок. |
| `T` меняется на ходу | `morph_phase` сохраняется, а окно кроссфейда зафиксировано на шаг (§4.1), поэтому `t` не прыгает. Безопасно при перетаскивании регулятора. Остаётся узкая щель: смена `T` в те самые 5 мс, когда фаза уже внутри окна, укорачивает текущий кроссфейд — один сокращённый переход, дальше норма. |
| `MOR` включают/выключают | Переключение между `buffer_carrier` и парой слотов не кроссфейдится — как и смена формы обычным спиннером несущей, которая всегда была мгновенной. `morph_phase` переживает выключение, но при следующем включении пара и фаза приводятся в порядок (строки выше). |
| FM включена | На метаморфозу не влияет: шаг считается своей фазой, а не фазой несущей. |
| Mono (`liveData.mono`) | Рендерится только `ch1` и дублируется в L/R — работает метаморфоза `ch1`. |
| Канал выключен | `!en_ch` → ранний `return`, метаморфоза не считается. |
| Имя формы в слоте не найдено | `Spinner_Send_Buffer` выходит, буфер слота остаётся нулевым → тишина на этом слоте. Ровно как сейчас у обычной несущей. |
| Противофазные формы | На `t=0.5` возможен провал громкости (§4.2). Не лечим. |

## 11. Тесты

Юнит (Kotlin, `app/src/test/...`) — на хелперы §5.2:

- `morphSteps(T, sr)` для `T ∈ {0.1, 2, 100}` → `== round(T*sr)`, всегда `≥ 1`
- `morphMask(s0,s1,s2)` → биты 0/1/2; все выключены → `0`
- `morphEffective(en, mask)` → `false` при `mask == 0` даже при `en == true`

Натив (`renderchannel.cpp`) — ручная проверка осциллографом и на слух:

- Плавно: форма непрерывно перетекает, разрыва на границе шага нет
- Ступень: смена формы без щелчка — обязательно на паре с разными краями таблиц,
  например `Sine` → `HWave2` (см. §4.4), иначе тест ничего не проверяет
- Период шага соответствует заданному `T` в обоих режимах
- Снятие галочки с текущего слота во время генерации — без щелчка
- Снятие галочки с целевого слота посреди перехода — без щелчка
- Перетаскивание регулятора `T` во время генерации — без щелчков и зиппера

**Известный пробел:** состояние метаморфозы (кривая `t`, границы шага, смена пары слотов)
автоматическими тестами не покрыто — в проекте нет инфраструктуры для нативных тестов, а из
JVM-юнит-тестов путь рендера недостижим. Именно эти четыре последних пункта чеклиста ловят
дефекты, которые тесты поймали бы дешевле. Если нативные тесты когда-нибудь появятся,
